# AIOS Architecture

## Current system

AIOS v0.5.0 is a desktop control-plane prototype. It is built as a Tauri 2 application with a React/TypeScript frontend and a Rust backend.

```text
┌──────────────────────────────────────┐
│ React + TypeScript UI                │
│ Overview · Projects · Processes      │
│ Models                               │
└──────────────────┬───────────────────┘
                   │ Tauri commands/events
┌──────────────────▼───────────────────┐
│ Rust application state               │
│                                      │
│ RuntimeState   ProjectsState         │
│ ModelsState                          │
└──────────────────┬───────────────────┘
                   │
             In-memory only
```

## Code map

| Path | Responsibility |
| --- | --- |
| `apps/desktop/src/App.tsx` | Desktop navigation, views, and Tauri IPC calls |
| `apps/desktop/src/App.css` | Desktop UI styles |
| `apps/desktop/src-tauri/src/lib.rs` | Registers managed state and exposed Tauri commands |
| `apps/desktop/src-tauri/src/core/state.rs` | Runtime and process lifecycle data |
| `apps/desktop/src-tauri/src/core/runtime.rs` | Runtime/process commands and runtime events |
| `apps/desktop/src-tauri/src/core/projects.rs` | Workspace registry and Git marker detection |
| `apps/desktop/src-tauri/src/core/models.rs` | Provider/model metadata and role defaults |
| `apps/desktop/src-tauri/capabilities/default.json` | Commands available to the main window |
| `apps/desktop/src-tauri/permissions/autogenerated/` | Per-command Tauri allow/deny permissions |
| `scripts/check-tauri-acl.mjs` | Checks command permission IDs against the capability |
| `.github/workflows/ci.yml` | Frontend, ACL, and Rust validation |

## State and lifecycle

The three Rust state stores are held in Tauri-managed memory:

- `RuntimeState` stores runtime status, process records, and a bounded event history.
- `ProjectsState` stores canonical workspace paths, active-project selection, and repository metadata.
- `ModelsState` stores provider metadata, model entries, and role defaults.

**All three stores reset when the desktop application exits.** No database, on-disk state format, migrations, or recovery behavior exists yet.

## Security boundaries

The default Tauri capability grants the main window access to the commands required by the current UI. The ACL validation script checks that the command permission identifiers and capability references stay aligned.

This is not an execution sandbox. Current commands do not expose a shell, arbitrary filesystem mutation, model inference, or external network calls. Project registration performs limited filesystem metadata checks on the path explicitly supplied by the user. Process resource values are validated and recorded, but they are not enforced by the operating system.

The implementation order for privileged capabilities is intentional:

1. Persist application state with versioned schemas and recovery behavior.
2. Define and test capability and permission enforcement.
3. Add process isolation and enforce resource/network limits.
4. Only then expose narrowly scoped tools, with audit records and human approval where appropriate.

Do not add terminal, filesystem-write, or network tools ahead of those controls.

## Data flow

The frontend invokes named Tauri commands and listens for typed state snapshot events:

- `aios:runtime`
- `aios:projects`
- `aios:models`

The backend owns state mutation. The frontend is a presentation and interaction layer; it should not become the source of truth for runtime state.

## Validation

The current CI workflow performs:

- `node scripts/check-tauri-acl.mjs`
- `npm ci` and `npm run build` (which includes TypeScript checking)
- `cargo test --lib`
- `cargo check`

A check being configured in CI is not evidence that it has passed. Verify the GitHub Actions run associated with the commit before describing a change as build- or test-verified.
